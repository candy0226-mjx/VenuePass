# 09 Java、MySQL 与性能基础

## 八股要能落到项目里

| 基础知识 | 在本项目中落在哪里 | 应能解释的因果 |
|---|---|---|
| BigDecimal | 订单金额、资源价格 | 二进制浮点误差、舍入与快照 |
| equals/hashCode | 用户 ID、Map、集合 | 包装类型不应使用 `==` 比值 |
| HashMap/Set | 关联数据批量组装、资源去重 | 哈希查找、冲突、线程安全 |
| Stream | seatIds 去重排序、金额累加 | 顺序、不可变结果、不能随意 parallel |
| JMM | 单例 Bean、线程间共享状态 | 可见性、有序性与原子性不同 |
| ThreadLocal | 日志业务 ID、安全上下文 | 线程复用、清理、异步传播 |
| JVM/GC | 导出、JSON、批量查询 | 大对象与暂停如何影响吞吐和锁续期 |
| 连接池/线程池 | HTTP、数据库、MQ 消费 | 线程增加不等于外部资源容量增加 |

## 金额、标识与时间

避免 `new BigDecimal(0.1)` 引入 double 近似值，优先字符串构造或合适的 valueOf。`equals` 比较还涉及 scale，`compareTo` 可用于数值比较。BigDecimal 不可变，add 返回新对象；真实计费必须明确小数位、折扣分摊和舍入策略。[S24](sources.md)

Long 是包装类型，`==` 可能只是在比对象引用，不能靠小整数缓存“碰巧正确”。UUID/时间戳订单号降低碰撞概率，数据库唯一索引才是持久约束；时间戳拼随机串也不是雪花 ID 算法。

`LocalDateTime` 不携带时区。数据库、JDBC、操作系统、消费者的时钟差会影响过期判定。跨区系统可明确以 UTC/Instant 存储和比较，再在边界展示本地时间。当前没有完整跨时区方案。

## 并发基础：不要把 volatile 当事务

volatile 解决特定读写的可见性和有序性，不把 `count++` 变成原子动作。synchronized/ReentrantLock 只协调当前 JVM；两台应用实例需要共享协调机制或依赖数据库原子约束。

happens-before 是推理线程间可见性的关系，不是“现实世界中时间先发生就一定看见”。本项目跨进程协调依赖 Redis/MySQL 协议语义，不能只用 Java 内存模型解释。

数据库 JDBC 事务通常绑定当前线程。随手用 `parallelStream` 写订单明细会改变执行线程和事务上下文，也可能加剧连接池竞争。当前没有启用 Java 21 虚拟线程，不要因 JDK 21 就说项目已经使用。

## MyBatis-Plus 做了什么，没有替你做什么

实体映射、条件构造器和通用 CRUD 减少样板代码；分页拦截器改写分页 SQL。它不会自动推导业务权限、为任意读改写加乐观锁，也不会看到 `updateById` 就自动在 WHERE 增加旧状态。

判断是否安全要看生成 SQL 的条件和影响行数，而非方法名看起来像“更新”。`@Version` 乐观锁需要相关字段、配置及正确用法，当前不应宣称全局启用。

## B+Tree 与索引访问

InnoDB 聚簇索引叶子保存记录，二级索引通常保存索引字段和主键。利用主键再取未覆盖字段常称回表；覆盖索引能减少这一步。B+Tree 的扇出让树高较小，叶子有序适合范围查询，不代表任何查询有索引都快。

联合索引看左侧字段与查询条件、范围、排序如何匹配；选择性、数据量和统计信息也影响优化器。不要机械说“status 低基数所以永远不能建索引”，`(status, expire_time, id)` 对待关闭订单扫描可能有意义，要实测。[S07、S21](sources.md)

```sql
-- 只查看执行计划，不修改业务数据
EXPLAIN SELECT id, expire_time
FROM reservation_order
WHERE status = 'PENDING' AND expire_time < NOW()
ORDER BY expire_time, id LIMIT 50;
```

先观察 key、估算 rows、过滤和排序；`EXPLAIN ANALYZE` 会实际执行查询，使用前了解成本。索引有写放大、空间和维护成本，不是越多越好。

## MVCC、锁与库存丢更新

MVCC 用版本链与读视图帮助一致性读减少读写冲突。RC 和 RR 的快照创建/使用规则不同；UPDATE/锁定读与普通快照 SELECT 不是同一类读。隔离级别不能把 Java 中“读到 2，算出 1，再 SET 为 1”的逻辑自动变成安全减一。[S10、S11](sources.md)

两个预约不同资源的请求都读到 `available_stock=2`，各自 `updateById` 写 1，最终 DB 为 1，但实际占位已有 2 个。资源唯一索引无法检测，因为 seatId 不同。可研究：

```sql
-- 改进示例；必须检查影响行数并与订单写入放在同一事务
UPDATE `session`
SET available_stock = available_stock - ?
WHERE id = ? AND available_stock >= ?;
```

释放也应做数据库内的原子加法，并由成功状态迁移决定只加一次。只把减库存改正确，不处理取消/关单的重复加，也不完整。

悲观方案可 SELECT ... FOR UPDATE 保护读改写，但会把同场次并发串到同一行，事务中不要等待长网络调用。死锁需要统一访问顺序、缩短事务、合适索引，并对可重试的完整事务有限重试；不要只补发一条中间 SQL。[S10](sources.md)

## 分页、N+1 与大结果集

页大小限制避免一次取无限数据。深 offset 仍可能扫描和丢弃大量行；可研究 `created_at + id` 稳定排序的游标分页。只有 created_at 时，同时间记录可能顺序不稳定。分页 count 也需要考虑大表成本。[S25](sources.md)

若按点评逐条查作者/图片，会产生 N+1。当前批量加载已经有可取之处，但要关注大 IN 列表、数据库参数上限和分页数据的一致性要求。

## 性能分析的顺序

先确认是客户端、网络、CPU、锁等待、DB、Redis 还是外部调用慢，再做优化。吞吐增加而 P99 变差通常说明队列或竞争积累，均值会掩盖长尾。

HTTP 工作线程、Hikari 连接、Redis 客户端连接、MQ 消费并发和磁盘都有上限。把线程池调成很大可能只会制造更多等待、内存和切换开销。线程池需定义并发数、队列上限、拒绝策略和超时，关键操作不使用无边界后台任务。
