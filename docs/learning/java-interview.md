## 先把术语说成人话

| 术语 | 容易理解的解释 | 不要误解为 |
|---|---|---|
| 原子性 | 在约定的机制和范围内，操作不能被观察成任意交错的几步 | Redis、MySQL、MQ 自动一起成功；Lua 报错一定撤销写入 |
| 可见性 | 一个线程的修改，其他线程能按同步规则观察到 | 整段业务自动不可分割 |
| 幂等 | 同一个操作重复执行，不多产生一次业务效果 | 每次响应文字必须一样；只拦按钮连点 |
| CAS | 比较当前值是否符合预期，符合才修改 | 数据库条件更新就是 CPU 的同一条指令 |
| 事务 | 把一组相关操作放到明确的提交和回滚范围内 | 所有外部系统、文件和通知都随它回滚 |
| 回表 | 从二级索引得到主键，再去聚簇索引取需要的数据 | 每次索引查询都必然查两遍 |
| 回源 | 缓存没有可用结果，再访问正式数据源 | Redis 挂了就无限放量查数据库 |
| 补偿 | 通过另一项业务操作修复已经发生的副作用 | 时间倒流；任何操作都能无损撤销 |
| 尾延迟 | 最慢那部分请求的耗时，如 P99 | 所有请求的平均耗时 |

## 一、Java 基础

主要参考：[Object](sources.md#s31)、[Java 类型与变量](sources.md#s32)、[BigDecimal](sources.md#s24)、[异常与资源关闭](sources.md#s47)。

### J01 面试官：`==` 和 `equals` 有什么区别？

**我：** 基本类型用 `==` 比值，对象引用用 `==` 比是不是同一个对象。`equals` 则取决于类怎么定义，比如 String 用来比较文字内容。

项目中订单 ID 是 Long 对象，比较 ID 应用 `equals` 或空值安全的 `Objects.equals`。不能因为测试时两个小数字用 `==` 正好成功，就认为所有 ID 都行，包装类型缓存可能掩盖问题。

**追问：Long 和 long 比较呢？**

**我：** 通常会发生拆箱再比数值，Long 如果为 null 就可能抛空指针。写业务条件时应先明确能否为空，不靠隐式拆箱碰运气。

### J02 面试官：重写 `equals` 为什么通常也要重写 `hashCode`？

**我：** 哈希集合先靠 hash 定位，再靠 equals 判断是不是同一个 key。如果两个对象按 equals 相等，却算出不同 hash，就可能无法按预期查找或去重。

项目用用户 ID 建 Map、用资源 ID 去重，Long 已经实现了这套约定。如果以后用自定义“场次 + 资源”对象当 key，就要一起定义比较和 hash。

**追问：hash 一样就说明对象相等吗？**

**我：** 不是，可能只是冲突，还要比较 equals。相等必须同 hash，同 hash 不必相等。

### J03 面试官：String 为什么不可变，有什么用？

**我：** 一个 String 创建后，它表示的字符内容不能原地修改。拼接或替换得到的是另一个结果，所以同一个字符串可以比较放心地共享，也适合当 Map 的 key。

项目的订单号和 Redis key 用字符串表达，但“字符串对象不可变”不代表“引用它的变量不能改”。不要把这两层混淆。

**追问：循环拼很多文字怎么办？**

**我：** 可以用局部 StringBuilder，避免不断产生中间结果。它适合同一线程组装内容；共享一个可变 StringBuilder 给多个请求就要考虑并发。

### J04 面试官：`final` 就是线程安全吗？

**我：** 不是。final 修饰引用，主要表示初始化后不能再把这个引用指向另一个对象；被引用对象的内容仍可能变化。

例如 `final List` 仍可能执行 add。项目构造器注入的 `final` Service 依赖让依赖关系稳定，但它们处理共享数据库数据时，仍需要事务和并发控制。

**追问：final、finally、finalize 是同一个概念吗？**

**我：** 不是。final 是修饰符，finally 用于退出时的清理逻辑，finalize 是已弃用并计划移除的终结机制，不应用它保证文件或连接及时关闭。

### J05 面试官：Java 是值传递还是引用传递？

**我：** 都是值传递。传对象时，复制的是引用这个值，所以方法内外可以指向同一个对象。方法修改对象字段，外面看得到；把参数重新指向新对象，不会改掉调用者变量的指向。

项目中把 DTO 传给 Service，就是传入同一个对象的引用副本，不是自动深拷贝。

**追问：`BeanUtils.copyProperties` 是深拷贝吗？**

**我：** 不能这样认为。它按属性复制值，嵌套可变对象可能仍共用引用。Entity 转 VO 时还要主动决定哪些字段允许返回，拷贝工具不负责数据权限。

### J06 面试官：金额为什么用 BigDecimal？

**我：** 钱要按十进制规则计算，double 对很多小数只能近似表示。比如 `0.1 + 0.2` 不适合作为精确结算依据。

项目把资源单价相加得到订单总价，使用 BigDecimal。还要规定小数位、舍入和数据库 DECIMAL 范围，构造时尽量从准确字符串或数据库金额开始。

**追问：为什么 `new BigDecimal("2.0").equals(new BigDecimal("2.00"))` 是 false？**

**我：** equals 同时看数值和 scale。只比较金额大小时通常用 compareTo，结果为 0 表示数值相同；add 返回新对象，也要接住计算结果。

### J07 面试官：受检异常和运行时异常怎么区分？finally 一定执行吗？

**我：** 受检异常需要调用方捕获或声明，RuntimeException 这类非受检异常没有这个编译要求。项目用 BusinessException 表达库存不足、状态冲突等业务失败，再统一转换成响应。

finally 通常会在方法正常返回或抛异常时执行，但进程被强制终止等情况下不能保证。不能仅凭 finally 或事务回调，就承诺进程崩溃后一定补偿成功。

**追问：释放资源还可以怎么写？**

**我：** 支持 AutoCloseable 的资源可以用 try-with-resources，按相反顺序关闭。它能改善正常执行路径的清理，但同样不能抵抗所有进程级故障。

### J08 面试官：泛型有什么作用，为什么 `List<String>` 不是 `List<Object>` 的子类型？

**我：** 泛型让编译器检查元素类型，减少到运行时才发现类型错误。如果允许把 List<String> 当 List<Object>，别人就能往里面加一个 Integer，破坏原来的约定。

项目里的 `ApiResult<T>`、`PageResult<T>` 都用泛型表达返回的具体数据类型。运行时大部分泛型信息经过擦除，不能把泛型当成完整的运行时业务校验。

**追问：`? extends T` 和 `? super T` 怎么记？**

**我：** 主要读取 T 可以考虑 extends，主要写入 T 可以考虑 super。但它们表达的是类型兼容范围，不等于集合一定可修改，也不提供线程安全。

## 二、集合与 Stream

主要参考：[ArrayList](sources.md#s34)、[HashMap](sources.md#s27)、[ConcurrentHashMap](sources.md#s35)、[Stream](sources.md#s33)。项目入口：[下单实现](../../src/main/java/com/jxbg/ticket/service/impl/ReservationOrderServiceImpl.java)、[点评结果组装](../../src/main/java/com/jxbg/ticket/service/impl/ReviewServiceImpl.java)。

### J09 面试官：List、Set、Map 怎么选？

**我：** 有顺序、允许重复的列表用 List；只关心某个元素有没有、要去重时用 Set；需要从一个 key 找到对应对象时用 Map。

项目用 List 接收资源 ID，之后去重排序；用 Set 判断资源占用；用用户 ID 到用户对象的 Map 组装点评。选择依据是业务操作，不是哪个类听起来高级。

**追问：Set 一定无序吗？**

**我：** 不是。HashSet 不承诺顺序，LinkedHashSet 保留插入顺序，TreeSet 按排序规则组织。要看具体实现，不能只看接口名。

### J10 面试官：ArrayList 和 LinkedList 有什么区别？

**我：** ArrayList 依靠数组，按下标取元素方便，顺序遍历通常也比较友好。LinkedList 依靠节点连接，随机定位需要走链，节点还有额外内存开销。

项目大多是查出一批数据、遍历和组装，用 ArrayList 往往更合适。不能简单背“链表增删一定快”，如果还要先找到位置，查找成本也要算进去。

**追问：什么时候预设 ArrayList 容量？**

**我：** 已知大致数量时可以预设，减少扩容复制。初始容量不是列表当前大小，也不要为了避免扩容一次分配过大的数组。

### J11 面试官：HashMap 为什么查询快，什么时候会慢？

**我：** 它通过 hash 把 key 分到不同桶里，再找具体元素。分布比较均匀时查找通常很快；冲突多、频繁扩容或 key 的比较很重，成本就会上去。

项目批量查作者后建立局部 Map，避免每条点评都再遍历用户列表。HashMap 不保证顺序，也不适合多个线程无保护地修改。

**追问：为什么不直接背“链表到八个就变树”？**

**我：** 树化还与容量等实现条件有关，具体过程应对照 JDK 源码。面试可以进一步解释，但不能把某个版本的阈值当成 HashMap 接口永久保证。

### J12 面试官：HashSet 怎样去重？对象放进去后还能修改吗？

**我：** 常见 JDK 实现用 HashMap 支撑，依赖 hashCode 和 equals 判断成员。项目资源 ID 是稳定的 Long，适合直接去重。

如果自定义对象用于计算 hash 的字段变了，它留在原来的桶里，之后可能查找或删除失败。所以集合 key 应尽量稳定，不能入集合后随意修改参与比较的字段。

**追问：两个 Seat 对象 ID 一样，就一定能 distinct 掉吗？**

**我：** 不一定，要看 Seat 的 equals 怎么定义。需要按 ID 去重时，先提取 ID 再去重通常更明确，不能把整个实体的相等规则直接当成业务身份规则。

### J13 面试官：ConcurrentHashMap 能保证整段业务线程安全吗？

**我：** 它提供线程安全的集合操作，但多次操作拼在一起不自动原子。例如先 containsKey、再 put，中间仍可能被其他线程插入。

需要“没有才放”时应考虑 putIfAbsent 或合适的 compute 操作。即便如此，Map 的安全也不代表里面的 ArrayList 等可变 value 安全，更不能用进程内 Map 代替跨实例的库存控制。

**追问：为什么不能用它的 size 判断库存还有没有？**

**我：** 并发修改时 size 只是某个时刻的观察，读完之后别人可以继续改。业务资格要用真正的原子条件操作判断。

### J14 面试官：Stream 的中间操作和终止操作有什么区别？

**我：** filter、map 这类中间操作是在描述处理步骤；collect、toList 等终止操作才触发实际消费。Stream 本身不是存储结果的容器，通常也不能重复消费同一个流。

项目的 `distinct().sorted().toList()` 表达去重、排序、收集资源 ID。不要把必须执行的写数据库逻辑塞进 peek 等中间操作，流优化和执行方式可能不符合预期。

**追问：`parallelStream` 一定更快吗？**

**我：** 不一定。任务拆分和协调有开销，阻塞调用还可能占用公共线程池。涉及 Spring 线程事务的写入，更不能直接改成并行就认为仍属于同一事务。

### J15 面试官：`Stream.toList()` 和 `Collectors.toList()` 一样吗？

**我：** 不完全一样。Java 21 的 Stream.toList() 明确返回不可修改列表；Collectors.toList() 不承诺具体实现和可修改性。需要可修改列表时，我会明确写 `toCollection(ArrayList::new)`。

项目的很多查询结果只用于遍历，toList 合适。如果后续想追加元素，就要调整收集方式。

**追问：不可修改列表里的对象能改吗？**

**我：** 如果元素本身可变，仍可能修改它的字段。不可修改列表主要限制结构变更，不是对每个元素做深度冻结。

### J16 面试官：`toMap` 和 `groupingBy` 在项目里怎么用？

**我：** 作者 ID 对应一个用户，可以用 toMap。一个点评有多张图片，是一对多关系，适合 groupingBy，把同一点评的图片放在一个列表里。

项目先批量查询，再按这些 Map 组装 VO，减少逐条查库。这个优化不等于只执行一条 SQL，页大小和批量 IN 的规模也要受控。

**追问：toMap 碰到重复 key 会怎样？**

**我：** 不带合并函数的常用重载会报错。应该先确认重复是否合理，再决定拒绝、合并还是保留某个值，不能随手写“取第一个”掩盖数据问题。

## 三、并发与线程

主要参考：[JMM](sources.md#s36)、[ReentrantLock](sources.md#s37)、[ThreadLocal](sources.md#s23)、[线程池](sources.md#s38)、[虚拟线程](sources.md#s42)。项目问题可接着练 [Q012](interview-questions.md#q012)、[Q025](interview-questions.md#q025)、[Q049](interview-questions.md#q049)。

### J17 面试官：进程和线程是什么关系？为什么项目会有并发问题？

**我：** 一个 Java 应用进程里有多个线程，线程可以共享堆中的对象。多个 HTTP 请求可能由不同工作线程同时处理，不是按我在页面上看到的顺序一件件执行。

部署多个应用实例后，各自内存不共享，但它们可能同时改同一套 MySQL 和 Redis，所以既有进程内问题，也有跨进程问题。

**追问：用了单例 Service，请求会排队执行吗？**

**我：** 不会，单例只是共用对象。没有额外同步时，多个线程仍能同时进入同一个方法。

### J18 面试官：原子性、可见性、有序性分别是什么？

**我：** 原子性关注操作会不会被拆开交错；可见性关注一个线程的修改，其他线程能否正确观察；有序性关注哪些执行和观察顺序受到保证。

比如两个请求都读到库存 2，再各自写 1，就是“读取、计算、写回”没有作为整体协调。让字段可见不等于修复了这个业务原子性问题。

**追问：把 Java 字段加 volatile，数据库丢更新能解决吗？**

**我：** 不能。数据库里的共享状态要由数据库条件更新、锁等机制协调，Java 字段修饰符管不到数据库事务竞争。

### J19 面试官：volatile 什么时候有用，什么时候不够？

**我：** 它适合让多个线程观察某个变量的新值，并提供相应顺序保证，例如简单停止标志。但 count++ 是读、算、写三步，volatile 不保证三步合起来原子。

项目如果做进程内计数，可以考虑原子类；实际预约数量跨应用实例，还要落到 Redis 或数据库的并发协议。

**追问：volatile 修饰一个对象，对象全部字段都线程安全吗？**

**我：** 不会。它首先作用于那个引用的读写和相关可见性规则，不会自动给对象内部的所有可变操作加锁。

### J20 面试官：synchronized 和 ReentrantLock 怎么选？

**我：** 两者都能做 JVM 内互斥，也支持同一线程重入。synchronized 使用比较直接，退出同步块会释放；ReentrantLock 提供可中断等待、尝试加锁、条件队列等更显式的能力，但要自己在 finally 正确解锁。

项目使用的 Redisson RLock 是跨实例协调工具，名字像 Lock，但还要考虑远程调用、租约和续期，不能和本地锁混为一谈。

**追问：公平锁一定更好吗？**

**我：** 不一定，公平性可能增加调度成本，吞吐也可能下降。是否需要公平，要看等待时间和业务需求，而不是默认公平就更高级。

### J21 面试官：CAS 是什么？ABA 又是什么？

**我：** CAS 是“当前值等于预期值才修改”。例如期望是 0，实际还是 0 才改成 1，别人已经改过就失败。

ABA 是值先从 A 变成 B，又变回 A，单看当前值会以为没变过。需要辨别变化历史时可以加版本号。数据库带 version 或 status 的条件更新有类似思想，但实现机制不是 Java 原子类那条 CPU 指令。

**追问：CAS 失败就无限重试可以吗？**

**我：** 不适合，竞争激烈时会浪费 CPU，还可能让延迟失控。业务操作也可能已经产生副作用，需要有限重试、退避和明确的重试范围。

### J22 面试官：死锁怎么发生，怎么降低风险？

**我：** 典型情况是 A 持有资源一等资源二，B 持有资源二等资源一，双方都不释放。可以通过统一获取顺序、缩小持锁范围、超时或失败重试降低风险。

项目对资源 ID 排序后尝试加锁，就是统一顺序。数据库涉及更多行和索引，仍可能产生其他死锁，不能因此说整个项目没有死锁。

**追问：`sleep` 会释放 synchronized 锁吗？**

**我：** 不会。Object.wait 在满足持锁要求时会释放它所等待的那个对象监视器，并在唤醒后重新竞争；其他已经持有的锁不会一起释放。等待业务条件时还应循环检查条件。

### J23 面试官：ThreadLocal 为什么能隔离请求数据，又为什么要 remove？

**我：** 它是按线程保存值，不同线程读取各自的那份。项目用它临时传递审计日志的业务 ID，但工作线程会复用，所以请求结束后必须清理，否则下一请求可能读到旧值。

常见实现里 key 是弱引用，但 value 仍可能被线程长期引用。不能把“弱引用”当成不用清理的理由。

**追问：InheritableThreadLocal 能直接解决线程池传递问题吗？**

**我：** 不能简单这么说。继承发生在创建子线程时，线程池经常复用已存在的线程，不是每次提交都创建。更可靠的是显式传必要字段，或使用经过验证并清理上下文的传播方案。

### J24 面试官：线程池有哪些关键参数，任务怎么进入线程池？

**我：** 我重点看核心线程数、最大线程数、队列、空闲时间、线程工厂和拒绝策略。典型执行过程是：核心线程未满就创建线程；之后尝试入队；队列满了再扩到最大线程数；仍接不住就拒绝。

因此无界队列可能让最大线程数难以发挥作用，还可能堆积任务。项目以后做异步导出时，不能只写一个线程池就结束，要约束队列和下游数据库容量。

**追问：CallerRunsPolicy 是不是保证任务绝不丢？**

**我：** 不能这样保证。它通常让提交线程执行任务，形成反压，但会拖慢请求线程；线程池关闭等情况还要按策略语义处理，任务执行本身也可能失败。

### J25 面试官：方法改成异步后，原事务和用户身份会自动过去吗？

**我：** 通常不会。Spring 常规 JDBC 事务与当前线程关联，切到异步线程后，不会自然加入原来的事务；SecurityContext 和日志上下文也不能假定自动传播。

比如把“保存订单明细”扔给后台线程，外层订单回滚时后台可能已经单独提交了。所以异步更适合在边界明确后处理独立工作，并传必要业务 ID。

**追问：CompletableFuture 的异常怎么处理？**

**我：** 要明确在哪个阶段观察、记录或传播异常，不能提交后就不看结果。异步返回成功也不表示任务成功；重要任务还需要持久状态和重试设计。

### J26 面试官：Java 21 的虚拟线程能直接让项目高并发吗？

**我：** 虚拟线程能降低很多等待型任务占用平台线程的成本，但不会凭空增加 CPU、数据库连接或数据库写入能力。仍需要控制访问下游的并发。

项目使用 Java 21，不代表已经启用虚拟线程。评估时还要结合这个 JDK 版本的阻塞和固定载体线程等行为，不把后续 JDK 的改进套到 Java 21 上。

**追问：要不要建一个很大的虚拟线程池？**

**我：** 虚拟线程通常面向每任务创建，而不是按传统方式池化来复用。限制数据库并发应使用连接池、信号量等明确机制，不靠线程便宜就无限提交。

<a id="jvm"></a>
## 四、JVM 与排障

主要参考：[JVM 运行时区域](sources.md#s39)、[类加载器](sources.md#s40)、[Java 21 G1](sources.md#s41)。项目入口：[Excel 导出](../../src/main/java/com/jxbg/ticket/service/impl/ExcelExportServiceImpl.java)。

### J27 面试官：堆、栈和元空间怎么理解？

**我：** 可以先这样理解：对象通常在堆里管理；线程执行方法需要自己的栈帧，保存局部变量和调用状态；HotSpot 元空间主要保存类元数据。实际优化可能改变对象的具体分配方式。

项目大量导出时会创建列表、行和单元格对象，主要需要关注堆压力；递归重试太深则要考虑线程栈。不能把所有内存错误都叫“堆不够”。

**追问：JMM 和 JVM 内存分区是同一件事吗？**

**我：** 不是。JVM 分区描述运行数据如何组织，JMM 主要描述线程之间读写共享变量的可见性和顺序约束。

### J28 面试官：GC 怎么判断对象能不能回收？

**我：** 常见追踪式 GC 从一组根引用出发，沿引用关系查找还可达的对象；不可达的对象才可能被回收，不是看代码有没有一个变量名叫它。

例如全局集合或长寿命线程仍引用着旧订单列表，即使业务已经不用了，它们也可能继续占内存。项目的 ThreadLocal 清理就是避免无用数据长期被线程保留。

**追问：两个对象互相引用，就一定不能回收吗？**

**我：** 不一定，如果这一整组对象都不能从根引用到达，追踪式 GC 仍可以回收。不能用简单引用计数的局限概括所有 Java GC。

### J29 面试官：G1 和 STW 是什么？项目用的哪种 GC？

**我：** G1 把堆划分成多个区域，结合并发处理和暂停阶段完成回收。STW 是某些阶段暂停应用线程，不代表整个 GC 全程都停，也不代表有并发阶段就完全没有暂停。

Java 21 HotSpot 在常见服务器配置下默认选择 G1，但项目实际进程用什么，需要看启动参数或运行信息，不能只凭 pom 写了 Java 21 就断言配置。

**追问：GC 暂停为什么可能影响 Redisson 锁？**

**我：** 如果暂停或调度延迟很长，续期线程也可能来不及执行，而 Redis 的租约时间仍在流逝。业务恢复后锁可能已不归自己，所以还需要数据库最终约束。

### J30 面试官：内存泄漏和 OOM 有什么区别？

**我：** 泄漏是业务不用的对象还被长期引用，无法回收；OOM 是运行时分配需要的内存等资源失败。OOM 可能由泄漏造成，也可能只是一次加载太多数据、线程太多或直接内存不足。

项目导出如果一次加载几十万条并建立完整工作簿，即使没有泄漏，也可能耗尽堆。解决要看证据，不能只把 Xmx 一直调大。

**追问：怎么区分正常占用和泄漏？**

**我：** 对比一段时间的 GC 后存活量、对象数量和引用链，结合请求量与任务是否结束。业务已经结束但存活对象持续增长，才是需要追踪的信号。

### J31 面试官：类加载和双亲委派有什么作用？

**我：** 类加载器把类定义加载进 JVM，常见加载流程先委托父加载器查找，再由自己尝试，帮助避免基础类被随意替换。类身份也与定义它的加载器有关。

项目出现“缺少类”或依赖冲突时，要查实际运行依赖和版本，不只是 IDEA 能不能跳转到源码。Maven 依赖存在、编译通过、运行时类兼容是不同层次。

**追问：`ClassNotFoundException` 和 `NoClassDefFoundError` 一样吗？**

**我：** 不一样。前者常见于显式加载找不到类；后者可能是运行链接时所需类不可用，也可能与类初始化失败有关。应该看完整 cause 和第一次失败日志，不只看最外层名字。

### J32 面试官：接口突然很慢，你怎么排查 JVM？

**我：** 先确认时间范围和受影响接口，再看 CPU、GC、堆占用和线程状态。用线程转储判断是在运行、等锁、等数据库连接还是等网络，再和 SQL、Redis 指标对齐。

高 CPU 不等于一定是 GC，低 CPU 也不等于服务没问题，线程全在等连接时就可能很慢。项目排障要关联订单 ID 和请求标识，避免只反复重启。

**追问：能直接导出堆文件看看吗？**

**我：** 可以作为诊断手段，但要先评估暂停、磁盘空间和敏感数据。先用低成本指标缩小范围，再决定是否采集堆，不能在不清楚影响时随手做重操作。

<a id="spring"></a>
## 五、Spring 与持久层

主要参考：[Bean 与依赖注入](sources.md#s43)、[AOP](sources.md#s04)、[事务](sources.md#s01)、[传播](sources.md#s02)、[Boot 自动配置](sources.md#s30)、[MyBatis](sources.md#s44)。只讨论项目版本已有的常用机制，不把最新版文档新增选项直接当作项目配置。

### J33 面试官：IoC 和依赖注入到底解决什么问题？

**我：** IoC 是把对象创建和协作交给容器管理，依赖注入是容器把一个对象需要的依赖提供给它。这样 Service 不用到处自己 new 数据访问对象。

项目通过构造器注入 Mapper、Redis 和其他 Service，依赖更明确，也方便测试时替换实现。Spring 还能在这些受管理对象外面加事务或日志代理。

**追问：自己 new 一个带 @Transactional 的类，会有事务吗？**

**我：** 不能仅靠注解生效。普通 new 出来的对象没有经过 Spring 事务代理，需要通过容器管理的正确调用路径。

### J34 面试官：Bean 大致经历什么生命周期？

**我：** 可以先按创建实例、注入依赖、初始化处理、投入使用、容器关闭时销毁来理解，中间有后处理器参与，代理也可能在这些流程里建立。

项目的 Redis 客户端等资源由容器管理，启动失败要看依赖和初始化异常，关闭时也应释放资源。不同作用域的管理范围不同，不能只背一条固定顺序覆盖所有 Bean。

**追问：prototype Bean 的销毁也一定由容器自动处理吗？**

**我：** 不是，容器创建并交出去后，通常不负责其完整销毁生命周期。持有它的代码要考虑资源释放。

### J35 面试官：循环依赖是什么，为什么构造器循环依赖难处理？

**我：** A 创建时需要 B，B 创建时又需要 A，两边都等对方先构造好，就无法正常完成。不能把“Spring 有三级缓存”理解成所有循环依赖都能解决。

如果以后订单服务和点评服务互相调用造成环，我会先重新划分职责，提取共同查询或编排服务。项目偏向构造器注入，更应该显式暴露这种设计问题。

**追问：加 @Lazy 或允许循环引用就算解决了吗？**

**我：** 有时能延后依赖获取，但不一定消除业务职责混乱，还要考虑代理和初始化时机。优先解决依赖方向，不能把开关当作所有循环的通用修复。

### J36 面试官：AOP 怎么让日志和业务分开？为什么自调用会失效？

**我：** AOP 通过代理在方法调用前后插入通用逻辑。项目的日志和限流切面就围绕目标方法执行，让 Controller 不必到处复制同样的代码。

调用从代理进入才会被拦截；同一个对象内部 this 调另一个方法，通常绕过代理，所以那个方法上的额外增强不会重新触发。事务也常用同样的代理机制。

**追问：写了 `@AfterReturning`，就表示数据库提交成功了吗？**

**我：** 不一定，它表示被它包住的调用正常返回。还要看这个切面和事务拦截器的嵌套顺序。真正依赖提交结果的动作，应使用明确的事务完成机制。

### J37 面试官：@Transactional 哪些情况下达不到预期？

**我：** 常见情况有绕过代理、自调用想开启新事务、异常被吃掉、回滚规则不匹配，以及换线程后不在原事务中。还要看使用了哪个事务管理器和资源。

项目很多写方法显式配置 `rollbackFor=Exception.class`。默认通常对 RuntimeException 和 Error 回滚，受检异常默认规则不同；但不能只加一个参数就解决外部 Redis 或 MQ 的一致性。

**追问：private 方法是不是一定没有事务？**

**我：** 它不能靠普通代理被单独拦截开启新事务，但如果外层已经在事务里，内部数据库操作仍可参与外层事务。要看实际调用路径。

### J38 面试官：REQUIRED、REQUIRES_NEW、NESTED 怎么区别？

**我：** REQUIRED 有事务就加入，没有就新建；REQUIRES_NEW 挂起外层，独立开启和提交；NESTED 在支持的事务管理器下通常依靠保存点，在同一物理事务里做局部回滚。

项目操作日志使用 REQUIRES_NEW，希望业务失败时日志还能保留。NESTED 如果外层最后回滚，内层所谓成功通常也保不住，所以两者不能互换。

**追问：内层 REQUIRED 抛异常，外层 catch 后就能照常提交吗？**

**我：** 不一定，内层通过事务代理参与同一事务时，可能已经把整个事务标记为只能回滚。外层即便吞掉异常，提交时仍可能得到 UnexpectedRollbackException。

### J39 面试官：Spring Boot 自动配置为什么“加依赖就能用”？

**我：** 依赖让相关类出现在 classpath，Boot 再根据类是否存在、属性和已有 Bean 等条件决定创建哪些默认组件。不是把所有 jar 中的类都创建一遍。

项目自己定义了 RedissonClient、SecurityFilterChain，MQ 还根据 enabled 属性选择组件。排查时要看条件和 profile，不能不停加 @Component 试运气。

**追问：starter、自动配置和组件扫描是同一件事吗？**

**我：** 不是。starter 主要组织依赖，自动配置按条件提供默认组件，组件扫描发现指定范围内的应用 Bean。它们相互配合，但各有职责。

### J40 面试官：MyBatis 的 `#{}` 和 `${}` 有什么区别？

**我：** `#{}` 通常生成预编译参数占位，把输入当参数值；`${}` 是直接拼接 SQL 文本，所以不能把未经验证的用户输入放进去。

项目主要使用 MyBatis-Plus 的 Wrapper 和 Mapper。普通参数绑定有帮助，但如果以后把排序字段或 SQL 片段交给前端，仍要使用服务端白名单，不能认为用了 ORM 就不会 SQL 注入。

**追问：列名和排序方向能用 `#{}` 随便传吗？**

**我：** 它是值参数，不是任意 SQL 结构替换。动态列名和 ASC/DESC 应从固定允许集合映射，不能直接拼接用户原文。

<a id="engineering"></a>
## 六、数据库与工程追问

### J41 面试官：ACID、MVCC 和锁各负责什么？

**我：** ACID 概括事务应有的原子性、一致性、隔离性和持久性；MVCC 通过数据版本支持合适的快照读取；锁协调部分读写竞争。它们不是可以互相替换的同一个机制。

项目的订单、明细和数据库库存放在事务里，但“库存不能超卖”这个业务规则仍需要正确 SQL 和约束。数据库不能猜到 Java 代码里算错了库存。

**追问：RR 就完全没有幻读相关问题了吗？**

**我：** 不能一句话概括。要区分普通快照读和锁定读，InnoDB 对不同读写路径有不同机制。项目应按具体 SQL 推演，而不是只背隔离级别名称。[MVCC](sources.md#s11)、[锁定读](sources.md#s10)

### J42 面试官：联合索引、最左前缀和索引失效怎么讲？

**我：** 联合索引按多个字段的顺序组织，常见有效访问需要利用左侧前缀。比如先按状态筛选、再按过期时间范围查，可以评估对应联合索引。

但“索引失效”不是万能解释。函数、隐式转换、选择性和查询返回比例都会影响计划；范围条件后面的列也不一定完全没用，还可能参与过滤或覆盖。应拿实际 EXPLAIN 说明。

**追问：status 只有几个值，就绝对不适合建索引吗？**

**我：** 不能这样说。它作为联合索引的前导等值条件，配合过期时间等字段可能有价值，仍要看分布、查询和成本。[索引](sources.md#s07)、[执行计划](sources.md#s21)

### J43 面试官：悲观锁和乐观锁在扣库存时怎么体现？

**我：** 悲观方式可以先锁定需要修改的记录，再检查和更新；乐观方式常通过旧版本或业务条件判断是否还能更新，失败就重新判断。

例如下面表达数据库内条件扣减的设计。项目实体叫 ReserveSession，实际表名是 `session`。必须检查影响行数，并和订单写入处于同一事务。这是改进示意，当前代码仍有读取旧值后 updateById 的路径。

```sql
UPDATE `session`
SET available_stock = available_stock - ?
WHERE id = ? AND available_stock >= ?;
```

**追问：这个条件 UPDATE 在数据库里完全不加锁吗？**

**我：** 不是，InnoDB 执行写入仍会使用相应锁。业务上采用条件竞争，不代表底层没有锁。示意 SQL 还需补项目实际的状态等约束。[Q012](interview-questions.md#q012)

### J44 面试官：HTTP 幂等是不是响应必须完全一样？

**我：** 不是，重点是重复相同操作的预期效果，不多产生一次。比如一次删除成功后再删除，响应可能不同，但不应该多删别的东西。

项目下单是 POST，需要服务端另外定义防重复协议。当前一次性令牌会拒绝再次提交，不会返回原订单 ID，因此要区分“限制重复执行”和“可安全重试并取得原结果”。

**追问：请求超时能直接再下一单吗？**

**我：** 不能直接认定第一次失败，应查询结果或使用有结果记录的幂等协议。当前需要完善结果关联和订单归属检查。[HTTP 语义](sources.md#s46)、[Q035](interview-questions.md#q035)

### J45 面试官：TCP、WebSocket、STOMP 是什么关系？

**我：** TCP 提供连接上的可靠字节流，WebSocket 在其上支持双向消息帧，STOMP 再定义连接、订阅和发送等消息命令。项目用 Spring STOMP 给在线用户发个人通知。

TCP 的可靠不等于每条业务通知都被用户读到。用户离线、进程重启或数据库回滚仍需要应用处理，所以项目还把通知存在数据库。

**追问：有 WebSocket，就不用轮询或查询接口了吗？**

**我：** 仍需要重连补查、未读查询和业务结果确认。长连接改善实时体验，数据库记录负责可追溯结果。[用户通知目标](sources.md#s19)、[Q055](interview-questions.md#q055)

### J46 面试官：Session、JWT、认证和授权有什么关系？

**我：** 认证先确定你是谁，授权再判断你能做什么。Session 常把会话状态放服务端；JWT 可以携带签名声明，由服务端验签验证，但即时撤销和角色变化仍需要额外设计。

项目用 Security + JWT 做身份和路由角色限制。普通用户有支付接口权限，还要检查订单是不是自己的；这一步是对象归属授权，不能漏。

**追问：CORS 配好，是不是接口就安全了？**

**我：** 不是，CORS 主要约束浏览器跨源访问行为，不代替认证、授权或防 CSRF。非浏览器客户端也不会因为 CORS 而无法直接调用接口。[Security](sources.md#s12)、[JWT](sources.md#s13)

### J47 面试官：超时、重试和连接池为什么要一起考虑？

**我：** 一个请求等数据库连接时仍占着应用资源；超时后如果马上无限重试，会增加更多请求，可能让本来慢的系统更慢。

我会给等待和调用设置合理上限，只对可重试错误做有限重试并退避，同时保证重复执行不会多扣库存。连接池上限要结合数据库容量，不是线程越多、连接越多就越快。

**追问：消费者异常一直重新入队就能保证不丢吗？**

**我：** 会造成无效循环和积压。应区分暂时故障和永久错误，设计重试次数、隔离与告警；当前 MQ 没有完整的可靠重试隔离方案。[确认机制](sources.md#s16)、[Spring 容器确认](sources.md#s45)

### J48 面试官：单元测试、集成测试、并发测试、压测有什么区别？

**我：** 单元测试聚焦小范围规则，例如状态是否允许转换；集成测试验证数据库、Redis、MQ 等真实协作；并发正确性测试重点检查竞争时有没有多卖、漏释放或状态冲突；压测再看给定负载下的吞吐和延迟。

它们不能互相冒充。文档工具测试通过，不代表支付流程通过；顺序调用接口成功，也不代表多人抢同一资源正确。当前这次修订只验证文档和维护工具。

**追问：怎么把测试结果写进简历才可信？**

**我：** 保留版本、环境、数据量、请求模型、业务断言和真实结果。没有报告就写机制和实现，别把计划做的测试或例子数字当成绩。[压测实践](sources.md#s22)、[实验模板](templates/lab-record.md)
