# 13 底层原理追问补充

本章把题库中容易继续追问的基础原理展开。理解方式是“机制 -> 为什么这样设计 -> 项目哪里用 -> 哪里不能外推”。它不是要求把 Java 全部源码背完。

## 自动配置为什么“加依赖就能用”

Boot 根据 classpath、条件注解、用户配置与已有 Bean 决定是否提供默认组件。例如发现相关 JDBC 依赖和连接配置后提供数据源等支持；用户提供自己的 Bean 时，某些默认配置会退让。不是把所有 jar 中的类都实例化，也不是 Maven 直接创建对象。

项目显式提供 RedissonClient、SecurityFilterChain 等配置，MQ 再用属性条件选择实现。排查 Bean 未创建时看依赖、扫描范围、条件结果、配置激活与构造器异常，而不是反复添加 `@Component`。[S30](sources.md)

## AOP 与装饰器的共同思想

把日志、事务、限流等可复用行为放在目标操作之外，避免每个业务方法复制。运行时代理能在进入和退出时拦截，前提是调用通过代理；装饰器可以显式包装同一接口。它们都不能自动处理目标方法内绕开边界的行为。

多个横切行为形成嵌套顺序：先进入的最后退出。哪个切面外包事务，决定它看到的是方法返回还是事务最终提交。不能把“后置通知”简单等同于“数据库提交之后”。[S04、S03](sources.md)

## HashMap 为什么快，为什么又不总是 O(1)

hashCode 把 key 分散到桶，equals 判断真正相等；良好分布下 get/put 期望成本较低。哈希冲突、扩容和遍历容量都影响实际成本。JDK 实现可用链表/树处理桶内冲突，具体阈值要按 JDK 源码确认，不能把阈值当 API 保证。

HashMap 不承诺遍历顺序，也不提供共享修改的线程安全。点评方法中局部建立的 Map 用于一次请求组装，和单例字段长期被多人修改是两种场景。对自定义 key，equals 相等必须有相同 hashCode，参与哈希的字段不宜入表后再变。[S27](sources.md)

## ThreadLocal 的 key 弱引用，为什么 value 还可能泄漏

JDK 常见实现由 Thread 持有映射，条目对 ThreadLocal key 使用弱引用，而 value 仍被条目强引用。key 回收并不使 value 立即消失；线程池里的长寿命线程可能保留这些值，直到清理路径处理。最直接的业务纪律是在 finally remove。

这也是日志上下文必须 clear 的原因。若切换线程，不应该假定用户上下文自动过去；显式传递必要字段，比把整个 Request 或 Authentication 长期挂在后台任务上更可控。[S23](sources.md)

## CAS、版本号与 ABA

CPU CAS 比较预期旧值和当前值，匹配才交换；数据库 `UPDATE ... WHERE status=?` 是类似的条件写入思想，但由 DB 的并发与锁语义实现，不能说它就是 CPU 的那条指令。

若状态 A 曾变 B 又回 A，只看值可能发现不了历史变化，这就是 ABA 思路。订单当前状态图没有随意重开流程，但未来重开/多阶段重试可能需要 version。只增加字段而不在更新条件中使用并递增，也不构成乐观锁。

## Redis“单线程”为什么不代表客户端多步原子

对当前使用的常规命令与 Lua，Redis 命令执行有串行语义，但客户端 A 的 GET 和 SET 之间完全可能执行客户端 B 的命令。I/O、后台持久化等也不能一概说只有一条线程。Redis 快还受内存访问、事件驱动、命令复杂度和网络影响，不能全归因于单线程。

Lua 把几步条件操作送到服务器一起执行；它越长，越会推迟其他命令。大 Set 操作、一次取全量榜单或昂贵脚本都可能制造长尾。Pipeline 只降低往返，不自动建立上述条件边界。[S05、S06](sources.md)

## Redis 数据落盘与复制能保证什么

RDB 是时点快照，恢复通常较紧凑，但快照间数据可能丢；AOF 记录写入操作，损失窗口与刷盘策略有关，也有重写成本。两者都不意味着数据库与 Redis 已处于同一业务提交点。[S28](sources.md)

复制通常异步，主节点已确认的写入可能尚未到副本。故障切换后锁、token 或预扣状态可能丢失。WAIT 等机制可增强某些确认条件，但不能直接变成任意故障下的强一致业务协议。项目没有完成这类高可用部署验证。[S29](sources.md)

## Redis 缓存淘汰与 TTL 是两件事

TTL 到期意味着 key 不再有效，达到内存限制时淘汰策略可能提前删除合格 key。缓存详情丢了可以回源，库存预占或防重 token 被淘汰则直接影响行为，因此不能把所有数据按同样“随便丢失也可重建”策略处理。

实际部署要区分可重建数据、协调数据和持久业务事实，监控容量、淘汰、过期与大 key。当前无 TTL 的库存/榜单也要定义保留期，否则生命周期失控；这里是工程规划，不是已实施配置。

## B+Tree 与哈希索引的取舍

B+Tree 以页为单位提供高扇出、有序叶子与范围访问；哈希适合等值定位，不能自然提供同样的有序范围。主键过大还会增大二级索引负担。不是因为项目用了 HashMap 就应该把数据库索引也改成哈希。

MySQL 看的是访问路径与成本：where 条件、排序、覆盖、扫描数量和回表。一个看似建对的索引，在数据分布改变后也需要重新评估统计和计划。[S07、S21](sources.md)

## MVCC、undo、redo 与 binlog 不要混淆

undo 参与回滚和旧版本构造；redo 参与崩溃恢复，binlog 是服务器层变更记录，可用于复制与恢复链路。它们职责不同，不能把“有日志”说成永不丢业务事件。

即使 DB 自己能恢复已提交订单，应用提交后没发出去的 MQ 仍不会因为 redo 自动补发；这正是 Outbox 要把“待发送事实”写进业务数据库的原因。深入日志刷盘与两阶段提交时，再结合具体 MySQL 版本和配置继续研究。[S11](sources.md)

## 线程池、连接池为什么会互相放大等待

一个 HTTP 线程等待一个数据库连接时，依然占用请求资源；请求越来越多，队列、超时与重试都可能增长。独立审计事务还可能让一个业务同时占外层与内层连接。

正确方向是测量等待在哪里，定义并发上限、队列容量、超时与拒绝，限制重试放大。虚拟线程能降低某些线程等待成本，但不能凭空增加 DB 连接与写入吞吐；当前项目也没有启用它。

## GC 如何影响“锁有看门狗所以安全”的说法

GC 长暂停可能让业务线程、续期调度与网络处理同时延迟，租约时间仍由外部系统流逝。恢复后业务可能继续执行，但锁资格已变化。仅调大 leaseTime 会增加失败后占用时间，不会消除全部问题。

先通过 GC 日志、线程与堆证据确认，再考虑减少大对象、限制导出并发或调整堆与回收器。不要看到接口慢就直接强制 Full GC 或换 GC 算法。

## TCP、WebSocket、STOMP 是什么关系

TCP 提供连接上的可靠字节流，HTTP/WebSocket 是更上层协议；WebSocket 支持双向帧，STOMP 再定义 CONNECT、SUBSCRIBE、SEND 等消息语义。TCP 不丢一个字节不代表应用业务事件永不遗漏，断线、进程重启与事务回滚仍需应用协议处理。

因此项目用数据库通知列表补离线消息，用 Principal 做个人路由，还需补订阅授权、重连和多实例协调。不能把 socket 建立成功当完整消息可靠性验证。[S19](sources.md)

## 为什么“最终一致”必须有恢复动作

“过一会儿就一致”不是机制。要指定事实源、事件标识、重试入口、去重条件、检查频率、超时告警和人工兜底。只写 catch 打日志，没有保证后续再执行，不能证明最终一致。

本项目定时扫描可补偿某些漏发关单触发，但并不自动修复所有 Redis 占位、计数、点赞和通知漂移。每一类数据都要定义自己的可接受误差和恢复协议。

## 常见设计模式如何对应实际代码

`OrderTimeoutMessageProducer` 的 MQ/空实现体现接口隔离与替换；切面体现横切关注点分离；状态校验类集中业务规则；Mapper/Service 分离数据访问与编排。说明这些具体收益即可，不必为每个 if 强行套一个模式名字。

对不清楚的问题，可以先说明已知边界，再提出如何通过文档、源码或实验验证。比给出一个自信但不成立的“绝对不会”更可信。
