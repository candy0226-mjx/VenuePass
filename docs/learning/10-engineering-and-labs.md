# 10 工程实践与实验

## 实验记录比“都测过了”更有用

下面是待执行实验方案，本次资料整理没有替你跑这些业务实验。所有写入、并发与故障注入只在独立测试库、独立 Redis DB 或专用 key 命名空间、独立应用实例中进行。准备新测试场次和资源，保留数据快照，不对日常开发中的有效订单反复改状态。

每次复制 [实验记录模板](templates/lab-record.md)，填写代码提交、环境版本、账号角色、数据 ID、步骤、预期、实际、日志和清理方式。发现偏差记录为失败，不为了凑“通过”而修改预期。

## L01 正常业务与数据模型

按 [原有接口流程](../api-test-flow.md) 获取用户 JWT、场次资源、下单 token，创建一个订单，查询订单/资源，模拟支付，核销员核销，用户发布点评，管理员审核，再由另一个用户点赞。

验收：每一步能对应数据库记录和合法状态；未核销不能点评，未审核不公开；每个账号的权限与对象归属分别验证。响应同时检查 HTTP 与 `body.code`。数据范围/归属失败不应被“正常路径跑通”掩盖。

## L02 事务回滚

在专用测试分支用调试器或受控异常让 createOrder 在 Lua 预扣后、数据库提交前失败，记录 Redis 数量、Set、订单表和明细表前后值。

预期：DB 无半条成功订单，正常回滚回调恢复预扣，资源锁最终释放，旧下单令牌不能再用。该实验不能证明进程崩溃窗口也正确，后者见 L04。

## L03 同座位与不同座位竞争

准备不同 USER 测试身份与独立 submitToken；本项目没有用户注册接口，可在测试数据中准备账号，不假定存在 `/register`。用屏障/统一开始时间释放请求，避免循环串行请求伪装成并发。

第一组多人抢同一 `sessionId+seatId`：预期有效占位最多一条。第二组同场次不同 seat：检查 DB 数量、Redis 数量与有效明细是否一致；这组用于暴露共享计数读改写风险。第三组多 seat 顺序反转，检查是否快速失败及是否有未释放锁。

当前业务限流会影响压力结果；必须记录限流阈值与 429 占比。不要偷偷把限流拒绝算作“抢购接口高吞吐成功”。

## L04 初始化与故障补偿窗口

在隔离环境把新场次库存 key 初始化步骤暂停在 SET 数量之后、SADD 占位之前，再发第二请求，观察是否见到半初始化状态。另用专用进程模拟预扣后退出，验证是否仅靠事务回调无法恢复。

验收不是要求当前代码一定通过，而是记录真实失败窗口。恢复前限制相关写入，核对有效订单与在途预占，执行有版本与作用域的重建方案。不要清空共享 Redis 或直接把已支付订单改成取消。

## L05 缓存命中与更新

查询一个新测试场馆，检查 `cache:venue:detail:{id}` 写入；重复读检查缓存；查不存在 ID 检查空值及 TTL；更新/停用后检查 key 是否失效。控制并发读写，推演旧值回填。

记录 DB SQL 次数、缓存值、TTL 和响应，而不只看接口耗时。新增前曾有空值缓存的 ID 也要单列测试，验证 createVenue 未主动失效的边界。

## L06 安全与幂等矩阵

使用两个普通用户 A/B、管理员和核销员：无 JWT、伪造/过期 JWT、角色不符、A 查询/支付/取消 B 的订单、A 传 B 的 userId、核销员传他人的 checkerId。

预期应由明确安全需求决定：非授权访问必须拒绝，当前存在的边界应记录为失败。测试同 token 连续/并发提交、两个 token 同资源、服务端成功但客户端超时后的重试。分别说明“防重”“返回同结果”“资源唯一”是否成立。

## L07 MQ 端到端

先按 [MQ 说明](../rabbitmq-delay-close.md) 在有真实 broker 的环境启用开关。用独立队列配置与短延迟测试：订单成功提交 -> 延迟队列 -> 关单队列 -> 消费 -> DB 与 Redis 释放。

测试已支付后到达、已取消后到达、重复消息、非法 orderId、消费者暂停后重启、broker 停机及发送后应用退出。若定时扫描也在执行，记录究竟是哪条路径关单；验证纯 MQ 路径时可在测试配置中将扫描间隔临时调长，测试后恢复，不能把扫描成功误算成 MQ 成功。

证据：消息路由、应用日志、订单状态、资源可用性、最老过期订单延迟。持久队列配置正确不等于消息故障恢复已经通过。

## L08 点赞、审批与副作用

同用户并发点赞/取消点赞；两个管理员同时批准与驳回；核对有效点赞记录数与 like_count，核对通知是否与最终审核状态一致。

故意令外层事务回滚，观察榜单分数和已推送通知是否仍变化。这是“DB 原子但外部副作用不回滚”的直观实验，不把暂时无异常当成分布式一致性证明。

## L09 文件与长连接

上传正常图片、超限文件、伪装扩展名、损坏图片；检查访问路径及非授权文件归属。用两个连接尝试正确和错误用户目标的订阅，测试重连、过期 JWT、离线通知补查。

当前扩展名校验和 CONNECT 验签只是基础，不预设这些安全用例都能通过。多实例验证时还需说明连接在哪个实例、simple broker 的局限。

## L10 查询与索引

在可重复生成的数据集上对订单扫描、用户订单、点评列表做 EXPLAIN，记录数据量、索引、执行计划与参数。把候选索引放在测试库比较读收益和写成本。

导出应测试空数据、上限、越权、内存和临时文件。SQL 检查可复用 [只读一致性查询](labs/check-invariants.sql)，它不会自动修复数据。

## L11 负载与瓶颈

按 [JMeter 官方实践 S22](sources.md) 在负载测试中使用非 GUI 运行并合理收集结果。先预热，再阶梯增加并发，分开测试场馆热读、冷读、下单与混合流量。

记录：提交版本、硬件、JVM 参数、实例数、中间件版本、数据量、持续时间、并发、请求总量、业务成功/失败、限流占比、吞吐、P50/P95/P99、CPU、堆/GC、连接等待、慢 SQL 和 Redis 延迟。

```text
业务成功率 = 业务code符合该用例成功定义的次数 / 总请求数
吞吐 ≠ 同时在线人数；P99 ≠ 平均耗时；HTTP 200 ≠ 业务成功
```

没有这些上下文就不写“支持万级并发”或任意 QPS。压测脚本本身也可能是瓶颈。

## L12 排障演练

场景：接口 HTTP 200、body.code=500。先确定时间、用户与业务 ID，查异常堆栈和依赖连接；核对 Redis 是否运行、DB 配置、事务提交状态，不直接重复创建订单。

场景：可约资源一直 false。查对应 session 下有效 order_item、订单状态和过期时间，再查 Redis 占位与数量；确认是正常已支付占用、应超时未释放，还是跨系统漂移。不要全局改 seat.status，因为它是资源启停而非某场次占用。

场景：消费积压。看 ready/unacked、消费速率、失败重试、DB 锁与连接等待；扩消费者前先确认幂等和数据库承载能力。

## 部署与变更纪律

- 使用环境变量和未提交的本地配置；示例凭据不用于公开部署。
- `CREATE TABLE IF NOT EXISTS` 不会自动迁移已有表结构；升级使用版本化 SQL、备份与兼容顺序。Flyway/Liquibase 尚未集成。
- 处理终止信号时停止接新请求、排空任务和连接；长连接与事务不能靠强制断电“优雅退出”。
- 日志记录请求关联 ID、业务 ID、错误码与耗时，敏感字段脱敏；监控业务失败而非只监控 HTTP 5xx。
- 变更表结构、Redis key 格式或 MQ 队列参数时设计旧新版本兼容与回退。

## 一份故障回答应包含什么

现象与影响 -> 已知事实 -> 缩小范围的方法 -> 验证根因 -> 有范围的止损 -> 修复与回归 -> 防再发。不要倒过来先说“我会加缓存/加机器”，也不要把演练说成真实生产事故。
