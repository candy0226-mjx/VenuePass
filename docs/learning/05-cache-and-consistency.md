# 05 缓存与一致性

## 场馆详情的真实读写路径

入口：[VenueServiceImpl](../../src/main/java/com/jxbg/ticket/service/impl/VenueServiceImpl.java)。读取先 GET；命中 JSON 就反序列化，命中空字符串返回不存在；未命中获取互斥锁，二次查缓存，再查数据库并写回。

正常数据 TTL 为 30 分钟加 0-5 分钟随机量；空值 TTL 为 2 分钟加 0-30 秒随机量。未取得锁会等待 50ms 后递归查询；锁等待 1 秒、固定租约 5 秒。当前没有“逻辑过期返回旧值并后台重建”，也没有 Caffeine 两级缓存。

更新或停用场馆：先 `updateById`，再删除详情缓存。`createVenue` 当前只保存，不主动删缓存。之前若对后来创建的 ID 缓存了空值，仍会等待空值过期。讲实现以源码为准，不照搬旧 README 中所有“新增也删缓存”的概括。

## 三种缓存异常要能给具体例子

| 问题 | 例子 | 当前缓解 | 仍有边界 |
|---|---|---|---|
| 穿透 | 不断查数据库不存在的场馆 ID | 空值缓存 | 随机的新 ID 仍持续打 DB，需校验/限流，必要时布隆过滤器 |
| 击穿 | 某热门场馆刚好过期，很多人同时查 | 互斥重建与二次判断 | 锁超时、递归重试和线程等待需要上限 |
| 雪崩 | 多个 key 集中过期，或 Redis 整体不可用 | 随机 TTL 分散到期 | 随机 TTL 不能解决 Redis 整体宕机 |

布隆过滤器是学习方案，项目尚未集成。其误判意味着“可能存在”仍需查 DB；动态新增数据也要维护过滤器。

## Cache Aside 为什么先改数据库再删缓存

数据库作为事实源；缓存可重建。先删缓存再更新 DB 时，期间有读请求可能查询旧 DB 并重新缓存。先改 DB 再删缓存通常更合适，但它依然不是跨系统强一致。

推演旧值回填：

```text
A: 缓存未命中，读取旧数据库值 v1
B: 数据库更新成 v2，删除缓存
A: 把较早读取的 v1 写回缓存
```

当前缓存重建锁只有读侧使用，写侧没有取得相同锁，因此不会自动消除这个时序。还可能发生 DB 更新已成功、删缓存失败，接口返回异常而缓存仍旧。

可选改进有：删除失败重试、基于事件的失效、与写侧协调、缓存版本校验。延迟双删只是降低特定时序概率，延迟长短和进程崩溃仍有问题，不能说成绝对一致。根据业务可容忍陈旧时间选择策略。[网上主题 C01；底层操作 S05、S06](sources.md)

## 为什么库存缓存比详情缓存更难

详情缓存是可重新查询的副本；库存 Redis 还包含数据库尚未提交的预占。直接按 DB 重建会遗漏在途预约，直接删除所有库存 key 会让运行中的补偿和新预约发生交错。

恢复步骤应先限制相关预约流量，确定数据库事实与在途预占，设计重建版本及原子发布，完成校验再恢复。不要把“清 Redis”当通用修复方法。

## Redis 宕机时怎样取舍

下单令牌、Lua 库存和分布式锁依赖 Redis，当前无法在 Redis 故障时完整运行下单。限流切面虽然发生异常会放行，但后续业务仍可能因为 Redis 不可用而失败。

场馆详情理论上可降级 DB，实际当前主要路径没有完整熔断/降级。若要放行到 DB，必须有请求速率、并发和连接池保护，否则会把 Redis 故障扩大为数据库故障。

要区分“可丢的热度”“可容忍短暂旧值的详情”“必须确认的库存与订单”。不同数据的持久化、过期与故障策略不应相同。

## 验证方法

L05 记录一次冷读、一次热读、一次改场馆后的读取，分别检查 DB 与 Redis。先用自己的测试 ID，不要删除无关 key。缓存过期测试可以在隔离环境对指定 key 设置短 TTL，保留前后记录。

排查命中率下降先看 TTL、key 命名、客户端序列化、穿透请求和容量淘汰，再看网络；不能因为用了 Redis 就预设数据库不可能是瓶颈。
